Non-Latin scripts (uk, el, hi, ja, ko, zh-cn) render through the OS font fallback, not a per-script webfont — see Type in DESIGN.md. Hindi needed its own fix: Devanagari vowel signs sit taller than Archivo's Latin metrics assume, so at the site's normal heading line-height (1.05–1.15) a wrapped `.display`/`.h2` heading's lines collided — fixed with a `:lang(hi)` override (loosened line-height, neutral letter-spacing/font-stretch since those are Latin-only concerns anyway); ja/ko/zh-cn needed no such fix. `ar`/`ur` (RTL, `dir: 'rtl'` in `i18n/config.ts`) closed out the full 22-locale roadmap. The site's logical-properties CSS discipline (see DESIGN.md) meant most of the site worked correctly under `dir="rtl"` with zero changes — browsers mirror flex/grid/table layout automatically. Three real RTL bugs found and fixed: (1) the calendar's week prev/next arrows are a plain flex row with no direction override, so RTL's automatic mirroring put "next week" physically on the left, inverting the "time runs left to right" rule the home chart already followed — fixed by adding `dir="ltr"` to that nav, same as `WeekChart`/`alert-strip`/`broken-chart` already do; (2) `.text-link`'s hover nudge (`translate: 3px`) runs in the page's own axes regardless of the `scale(-1,1)` mirror beside it, so a now-left-pointing arrow slid right on hover — fixed with a `[dir='rtl']` override reversing the nudge; (3) `LegalPage`'s content is untranslated English in every locale already (not just ar/ur), so under `dir="rtl"` it was right-aligning genuine English prose and moving list bullets to the wrong side — fixed with `dir="ltr"` on the component, now visually identical to the English page (verified side by side). 22 locales are live — the full extension language list is now covered.

## Working rules used so far
- Every page: independent finish review (fresh agent), Lighthouse/PageSpeed, no horizontal overflow at 320 px, both themes; fix in one batch, re-verify with the same reviewer.
- Extension code is never changed from this repo; report issues instead. The copy in `extension/` is outdated.
- Commit messages explain why; every push to `main` deploys the site (and the API when `server/` changes).
- **Run `npm run build` locally before pushing** (not just `next dev`, which doesn't type-check). A failed Vercel build silently keeps serving the previous deployment — new/changed pages 404 or look stale, and a manual Redeploy of the same broken commit just fails again. This bit the legal-pages push: `next dev` never caught a TypeScript error that `next build` did (JSON-sourced string fields widen to `string`, not a literal union — type unions from JSON content need a loose `type: string` field, checked at render time, not a literal type).
